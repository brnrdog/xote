# Reviewing xote code

The ReScript compiler cannot catch xote's characteristic bug. A one-shot signal
read has the same type as a reactive one; the difference is *when* the read
happens, and the only evidence is a UI that renders a correct first frame and
then stops. This review looks for that class of defect specifically.

If you have not loaded the `xote` skill in this session, read its SKILL.md
first — the checks below assume its model.

## Scope

Default to the current diff (`git diff`, or the PR's changed files). Review
whole files only when asked to, or when a diff's correctness genuinely depends
on surrounding code — a prop's reactivity, for instance, is decided at the call
site, which may be outside the diff.

## Checks, in priority order

### 1. Frozen leaves (critical)

Reactivity follows the expression literally written in JSX position. Flag:

- a signal read hoisted into a `let` and then used in JSX:
  `let n = Signal.get(count)` … `{n}`
- a value in JSX position produced by a call into **another module**:
  `{Store.remaining(store)}` — nothing in the name says "signal"
- a signal read inside a helper that is imported rather than defined in the
  same file

Not a defect: a `() => …` thunk, a `Computed`, `MaybeSignal.reactive(…)`, or a
read written inline in JSX position in an annotated file.

Fix: wrap in `() => …`.

To find candidates:

```bash
rg -n 'let \w+ = .*Signal\.get' -g '*.res'
```

then check whether each binding is used in JSX. Verify before reporting — an
intentional one-shot initial value is fine, and common.

### 2. Missing `@xote.component`, or missing the PPX (critical)

An annotation only decomposes the file it appears in, and only when
`"ppx-flags": ["xote/ppx/ppx"]` is in `rescript.json`. A file that reads signals
inline in JSX with **no** `@xote.component` anywhere compiles those reads as
one-shot values. An unknown attribute is silently ignored, so a missing
`ppx-flags` entry produces no error at all — every inline read in the project is
frozen.

```bash
rg -l '@xote\.component' -g '*.res' | head
rg -n 'ppx-flags' rescript.json
```

### 3. Unthunked user-component props (high)

`<Card label={Signal.get(name)} />` is a one-shot read by design: props land in
a typed record and the component body runs once. Flag any `Signal.get` /
`MaybeSignal.get` in a prop position on a **capitalized** component, unless the
component itself is rebuilt whenever that value changes (which is usually the
bug next door — see check 5).

Fix: pass the `Signal.t` or `MaybeSignal.t` down and read it inside.

### 4. Unkeyed lists (high)

`View.each`, or `<View.For>` without `by`, rebuilds every row on any change:
input state, focus, and per-row reactive state are lost, and the DOM work is
proportional to the whole list.

```bash
rg -n 'View\.each\(|<View\.For' -g '*.res'
```

Flag any list of items with stable identity. A short static list is fine. An
array index used as a key is a defect in its own right.

### 5. Oversized reactive scopes (medium)

A `View.tracked` block — written by hand, or generated by the PPX around an
`if`/`switch` in child position — replaces its children **wholesale**. Flag:

- a list rendered inside a tracked block: the reconciliation is thrown away on
  every condition change
- a form or anything holding DOM state (focus, scroll, media) inside one
- a tracked block wrapping a large subtree where only a small part varies

Fix: shrink the scope. Move the conditional into the row, use `View.Show`
around the smallest varying subtree, or feed a computed into the list.

### 6. Lifetime and cleanup (medium)

- `Computed.make` whose result is stored and never `Computed.dispose`d, in code
  that unmounts. Computeds also auto-dispose when they lose every subscriber,
  so this matters for long-lived ones you hold yourself.
- `Effect.run` **outside** a component render — module level, inside an event
  handler, in a callback. Nothing owns it, so it runs forever. Use
  `Effect.runWithDisposer` and keep the disposer.
- An effect body returning `unit` instead of `None` will not compile, but an
  effect that subscribes something it only meant to read (`Signal.get` where
  `peek` was meant) compiles and re-runs constantly.

### 7. Attribute correctness (medium)

- presence-based CSS (`[data-open]`, `data-checked:…`) fed by an attribute that
  is always present, even as `""` — it always matches. Needs
  `View.optionalComputedAttr(key, () => cond ? Some("") : None)`.
- an ARIA attribute expected to disappear when false. It should not: ARIA is
  enumerated and renders literal `"false"`.

### 8. SSR and hydration (medium, only in SSR projects)

- `SSRState.clear()` missing between server renders — state leaks across
  requests.
- `Router.init()` on a server path; must be `Router.initSSR(~pathname, ())`.
- server and client building state from different `SSRState` ids, rather than
  calling one shared factory.
- non-deterministic values (timestamps, randomness, locale formatting, `window`
  reads) rendered on both sides without syncing.

### 9. Deprecated and internal API (low)

```bash
rg -n '\bProp\.|View\.isReactiveProp|Route\.(parsePattern|matchPath|compile|matchCompiled|matchPathname)' -g '*.res'
rg -n 'Runtime[A-Z]\w*' -g '*.res'
```

`Prop` → `MaybeSignal`. The deprecated `Route` helpers → `Route.match`. A
`Runtime*` module is internal and not part of the public API.

### 10. Build hygiene (low)

- a hand-edited `.res.mjs` (compiler output — check `git status` for one changed
  without its `.res`)
- JSX-level `key` props, which are ignored; keys come from `by` / `eachWithKey`

## Verify before reporting

Every finding needs a concrete failure story: *which* value goes stale, on
*which* interaction, and what the user sees. If you cannot write that sentence,
the finding is speculation — drop it.

Two cheap ways to confirm:

- **Compile it.** `npx rescript`. Some findings turn out to be type errors, and
  a review that does not compile the code is guessing.
- **Look for the runtime evidence.** Xote wraps leaves it could not resolve in
  `View.probe`, which logs `[Xote] File.res:line: this value reads a signal
  through a call` on first evaluation in development. If the app can be run,
  that console output is a confirmed list of check-1 defects with line numbers.

## Report

Group by severity, most severe first. For each finding give the location, the
one-sentence failure story, and the fix as a diff-sized change. Do not restate
the checklist — report what is actually there, and say so plainly when a check
came back clean.
