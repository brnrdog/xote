In this tutorial you'll build a small temperature converter, one step at a time. Along the way you'll use the three ideas everything in Xote is built on: a **signal** holds a value, a **computed** derives a new value from it, and an **effect** does work outside the page when a value changes.

It assumes you have a project set up. If you don't, follow the [Quick start](/docs/quick-start) first; it takes a few minutes.

## Step 1: Show a temperature

Start with a component that displays one temperature. It takes the value and a unit as props and renders them as text. There's nothing reactive yet: it's a plain function that returns some markup.

```rescript
// TemperatureDisplay.res
type tempUnit = Celsius | Fahrenheit | Kelvin

let symbolFor = unit =>
  switch unit {
  | Celsius => "°C"
  | Fahrenheit => "°F"
  | Kelvin => "K"
  }

let labelFor = unit =>
  switch unit {
  | Celsius => "Celsius"
  | Fahrenheit => "Fahrenheit"
  | Kelvin => "Kelvin"
  }

@xote.component
let make = (~value: float, ~unit: tempUnit) =>
  <div class="temp-display">
    <span class="temp-value"> {value->Float.toFixed(~digits=1)} </span>
    <span class="temp-unit"> {symbolFor(unit)} </span>
    <span class="temp-label"> {labelFor(unit)} </span>
  </div>
```

Render it from your entry file:

```rescript
// App.res
View.mountById(<TemperatureDisplay value=22.0 unit=Celsius />, "app")
```

## Step 2: Make it react to a slider

Now let the reader change the temperature. Put the value in a **signal**, a container that remembers who reads it and tells them when it changes. A range input writes to the signal, and the display reads from it.

The display changes in two small ways: its `value` prop becomes a `Signal.t<float>`, and it reads that signal with `Signal.get`.

```rescript
// TemperatureDisplay.res (changed lines)
@xote.component
let make = (~value: Signal.t<float>, ~unit: tempUnit) =>
  <div class="temp-display">
    <span class="temp-value"> {Signal.get(value)->Float.toFixed(~digits=1)} </span>
    // …the unit and label spans stay the same
  </div>
```

Then a converter component owns the signal and the slider:

<DocsExamplePanel
      filename="Converter.res"
      caption="Drag the slider: the number follows."
      code={`let celsius = Signal.make(22.0)

@get external target: Dom.event => {"value": string} = "target"

let onSlide = evt =>
  switch Float.fromString(target(evt)["value"]) {
  | Some(value) => Signal.set(celsius, value)
  | None => ()
  }

@xote.component
let make = () =>
  <div>
    <TemperatureDisplay value=celsius unit=Celsius />
    <input
      type_="range"
      min="-20"
      max="40"
      step="0.5"
      value={Signal.get(celsius)->Float.toString}
      onInput=onSlide
    />
  </div>`}
    >
      <TutorialStep2 />
    </DocsExamplePanel>

A few things to notice:

- The `@get external` line is a one-line binding that reads `event.target`, so the handler can get the slider's value as a string.
- `Signal.set` writes a new value. Everything that read `celsius` with `Signal.get` updates.
- The display receives the **signal itself**, `value=celsius`, not its current value. A component's props are read once when it's created, so the signal is what lets the display keep up.

**Takeaway:** state lives in signals; reading one with `Signal.get` inside your markup keeps that spot up to date. Read more in [Signals](/docs/learn/signals).

## Step 3: Derive Fahrenheit and Kelvin

Fahrenheit and Kelvin aren't new state; they're always worked out from Celsius. That's a **computed**: a value defined by a function of other signals. It recalculates by itself when those signals change, and you never set it directly.

<DocsExamplePanel
      filename="Converter.res"
      caption="One signal drives three readouts. The panel lists every text change the page makes."
      code={`let celsius = Signal.make(22.0)
let fahrenheit = Computed.make(() => Signal.get(celsius) *. 9.0 /. 5.0 +. 32.0)
let kelvin = Computed.make(() => Signal.get(celsius) +. 273.15)

@xote.component
let make = () =>
  <div>
    <TemperatureDisplay value=celsius unit=Celsius />
    <TemperatureDisplay value=fahrenheit unit=Fahrenheit />
    <TemperatureDisplay value=kelvin unit=Kelvin />
    <input
      type_="range"
      min="-20"
      max="40"
      step="0.5"
      value={Signal.get(celsius)->Float.toString}
      onInput=onSlide
    />
  </div>`}
    >
      <TutorialStep3 />
    </DocsExamplePanel>

A computed *is* a signal, so `TemperatureDisplay` accepts `fahrenheit` and `kelvin` without any changes.

Drag the slider and watch the panel next to the demo. It records every change the page makes to its text. Each move changes exactly three text nodes, the three numbers, and nothing else: no components run again and no markup is rebuilt. That's the core idea behind Xote; [Thinking in signals](/docs/thinking-in-signals) explains it in more depth.

**Takeaway:** if a value can be worked out from other values, make it a computed instead of a second signal you have to keep in sync. Read more in [Computeds](/docs/learn/computeds).

## Step 4: Fetch the weather with an effect

Finally, show the real temperature in a world capital. Talking to the network is work outside the page, which is what an **effect** is for: a function that runs once, then runs again whenever a signal it read changes.

First, a few helpers: a list of capitals, ways to pick one, and a function that asks the free [Open-Meteo](https://open-meteo.com) API for the current temperature. The two `type` declarations describe the part of the JSON response we use.

```rescript
// Weather.res
type capital = {name: string, lat: float, lng: float}

let capitals = [
  {name: "Paris", lat: 48.8566, lng: 2.3522},
  {name: "Tokyo", lat: 35.6762, lng: 139.6503},
  {name: "Nairobi", lat: -1.2921, lng: 36.8219},
]

let pickCapital = () => capitals->Array.getUnsafe(Math.Int.random(0, Array.length(capitals)))

let otherCapital = (current: capital) => {
  let others = capitals->Array.filter(capital => capital.name != current.name)
  others->Array.getUnsafe(Math.Int.random(0, Array.length(others)))
}

type response
type currentWeather = {temperature: float}
type forecast = {current_weather: currentWeather}

@val external fetch: string => promise<response> = "fetch"
@send external json: response => promise<forecast> = "json"

let fetchTemperature = async (capital: capital) => {
  let url =
    "https://api.open-meteo.com/v1/forecast" ++
    `?latitude=${capital.lat->Float.toString}` ++
    `&longitude=${capital.lng->Float.toString}` ++ "&current_weather=true"
  let response = await fetch(url)
  let forecast = await json(response)
  forecast.current_weather.temperature
}
```

The card keeps the selected capital in a signal. Its effect reads that signal, so picking another capital runs the effect again and fetches new data. The computeds from step 3 are unchanged; only where `celsius` gets its value from is new.

<DocsExamplePanel
      filename="WeatherCard.res"
      caption="Real weather from a world capital. Try another one."
      code={`open Weather

type status = Loading | Ready | Failed

let rowClass = status =>
  switch status {
  | Loading => "temp-row is-loading"
  | Failed => "temp-row is-failed"
  | Ready => "temp-row"
  }

let statusText = status =>
  switch status {
  | Loading => "Fetching the current weather…"
  | Failed => "Couldn't reach the weather service."
  | Ready => "Live from Open-Meteo."
  }

@xote.component
let make = () => {
  let capital = Signal.make(pickCapital())
  let status = Signal.make(Loading)
  let celsius = Signal.make(0.0)
  let fahrenheit = Computed.make(() => Signal.get(celsius) *. 9.0 /. 5.0 +. 32.0)
  let kelvin = Computed.make(() => Signal.get(celsius) +. 273.15)

  Effect.run(() => {
    let current = Signal.get(capital)
    let stale = ref(false)
    Signal.set(status, Loading)

    fetchTemperature(current)
    ->Promise.thenResolve(temperature =>
      if !stale.contents {
        Signal.set(celsius, temperature)
        Signal.set(status, Ready)
      }
    )
    ->Promise.catch(_ => {
      if !stale.contents {
        Signal.set(status, Failed)
      }
      Promise.resolve()
    })
    ->ignore

    Some(() => stale := true)
  })

  let shuffle = _ => Signal.update(capital, otherCapital)

  <div>
    <h3> {"Now in "} {Signal.get(capital).name} </h3>
    <div class={rowClass(Signal.get(status))}>
      <TemperatureDisplay value=celsius unit=Celsius />
      <TemperatureDisplay value=fahrenheit unit=Fahrenheit />
      <TemperatureDisplay value=kelvin unit=Kelvin />
    </div>
    <p class="status"> {statusText(Signal.get(status))} </p>
    <button onClick=shuffle> {"Try another capital"} </button>
  </div>
}`}
    >
      <TutorialStep4 />
    </DocsExamplePanel>

Three details are worth a closer look:

- **The cleanup.** The effect returns `Some(() => stale := true)`. Xote runs that function before the effect runs again. If you switch capitals before a slow response arrives, the old request is marked stale and its result is ignored, so it can't overwrite the newer one.
- **No layout shift.** The readouts never leave the page. While a request is in flight, `rowClass` adds `is-loading`, and the stylesheet swaps each number for a placeholder of the same size; the status line below always holds one line of text. Switching capitals, or a failed request, changes classes and text, never the layout. Only the `class` attribute and the status text depend on `status`, so those are the only things that update when it changes.
- **The signals live inside the component.** Each card has its own state, and its effect stops when the card is removed from the page.

**Takeaway:** use effects for work outside the page, like requests, timers and storage, and return a cleanup whenever there's something to undo. Read more in [Effects](/docs/learn/effects).

## Bonus: let a resource do the work

Step 4 tracks the loading state by hand: a `status` signal, a stale flag, and a `switch` over the outcome. Xote has built-ins for exactly this, and the card gets shorter with them:

- A **resource** runs an async function and keeps its result in a signal: `Pending`, then `Ready(value)`, `Refreshing(value)` while it fetches again, or `Failed(error)`. Signals it reads before its first `await` are its inputs, so changing `capital` fetches again, and a late answer for an old capital is ignored for you.
- **`View.Suspense`** shows a fallback until the resources created inside it have loaded once. Here the fallback is the same placeholder cards as before, so there's still no layout shift.
- **`View.ErrorBoundary`** catches an error thrown while rendering and shows a fallback with a `retry` function. The readouts throw when the resource fails, and the boundary shows a panel the same size as the readouts.

<DocsExamplePanel
      filename="WeatherCard.res"
      caption="The same card on Resource, Suspense and ErrorBoundary."
      code={`open Weather

module WeatherReadouts = {
  @xote.component
  let make = (~capital: Signal.t<capital>) => {
    let weather = Resource.make(() => fetchTemperature(Signal.get(capital)))
    let celsius = Computed.make(() => Signal.get(weather)->Resource.value->Option.getOr(0.0))
    let fahrenheit = Computed.make(() => Signal.get(celsius) *. 9.0 /. 5.0 +. 32.0)
    let kelvin = Computed.make(() => Signal.get(celsius) +. 273.15)

    <div>
      <div class={Resource.isLoading(Signal.get(weather)) ? "temp-row is-refreshing" : "temp-row"}>
        <TemperatureDisplay value=celsius unit=Celsius />
        <TemperatureDisplay value=fahrenheit unit=Fahrenheit />
        <TemperatureDisplay value=kelvin unit=Kelvin />
      </div>
      <p class="status">
        {switch Signal.get(weather) {
        | Failed(error) => throw(error)
        | Refreshing(_) | Pending => "Updating…"
        | Ready(_) => "Live from Open-Meteo."
        }}
      </p>
    </div>
  }
}

@xote.component
let make = () => {
  let capital = Signal.make(pickCapital())
  let shuffle = _ => Signal.update(capital, otherCapital)

  <div>
    <h3> {"Now in "} {Signal.get(capital).name} </h3>
    <View.ErrorBoundary
      fallback={(_error, retry) =>
        <div class="error">
          <LoadingReadouts />
          <div class="error-message">
            <p> {"Couldn't reach the weather service."} </p>
            <button onClick={_ => retry()}> {"Try again"} </button>
          </div>
        </div>}>
      <View.Suspense fallback={<LoadingReadouts />}>
        <WeatherReadouts capital />
      </View.Suspense>
    </View.ErrorBoundary>
    <button onClick=shuffle> {"Try another capital"} </button>
  </div>
}`}
    >
      <TutorialStep5 />
    </DocsExamplePanel>

What changed from step 4:

- **The resource replaces the effect, the `status` signal and the stale flag.** `Resource.make` takes the fetch; `Resource.value` reads its result, with `0.0` until there is one.
- **The component that creates the resource sits inside the `Suspense`.** That's what makes the Suspense wait for it. `LoadingReadouts` is the step 1 display three times, with the placeholder class on its row.
- **After the first load, the Suspense stays out of the way.** Picking another capital moves the resource to `Refreshing`: the old numbers stay on screen, dimmed, until the new ones arrive.
- **A failure goes to the boundary.** `throw(error)` in the status line hands the failure to the nearest `View.ErrorBoundary`. Its `retry` renders the readouts again, which creates a fresh resource and fetches again. The fallback lays its message over hidden placeholder cards, so it takes exactly the readouts' space at any width.

**Takeaway:** for data that loads, reach for a resource. Suspense and error boundaries keep the loading and failure states out of your component's logic. Read more in [Async data](/docs/learn/async-data) and [Refs and lifecycle](/docs/learn/lifecycle#contain-errors-with-a-boundary), and see the [Fetching data](/docs/guides/fetching-data) guide for more recipes.
