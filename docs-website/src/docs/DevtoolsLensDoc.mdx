`xote-lens` renders a component headlessly, drives it, and explains its reactive behaviour. Everything it prints is also available as JSON and as MCP tools, so an AI agent can check its own work the way a person would: build, render, click, and read what happened.

> **Info:** xote-lens is not published to npm yet. Run it from a Xote checkout with `node path/to/xote/lens/bin/xote-lens.mjs`. The commands below write it as `xote-lens`. The reactive graph also needs the unreleased `rescript-signals` hooks; see [Try It Before the Release](/docs/devtools/overview#try-it-before-the-release).

## Getting Started

### Running It

Run it from anywhere inside a ReScript project (it finds the nearest `rescript.json`), or pass `--root`. Build the project first: `render` loads the compiled `.res.mjs` files.

```sh
alias xote-lens="node ~/src/xote/lens/bin/xote-lens.mjs"

xote-lens api View.tracked
xote-lens check
xote-lens render Counter --act "click #inc" --why "#value"
```

Add `--json` to any command for machine-readable output.

### Targets

A target is a compiled module name, optionally followed by an export path:

| Target | Renders |
|---|---|
| `Counter` | `Counter.res`'s `make` |
| `App.Header` | the nested module `Header`'s `make` |
| `App.view` | the export `view`, a component or a node |

## Commands

### api

The public API, read from Xote's `.resi` interface files. Everything it lists is public, and nothing else is.

```sh
xote-lens api                   # the public modules
xote-lens api View              # one module's declarations
xote-lens api View.Show         # a nested module and its members, with docs
xote-lens api --digest          # the whole surface as compact Markdown, for an agent's context
```

### check

Builds the project, then reports compiler errors and warnings, plus findings specific to Xote. Its exit code is non-zero when there is an error.

```sh
xote-lens check
```

```text
check: ok
  0 errors, 1 warning, 0 info
diagnostics:
  warning one-shot-prop src/Counter.res:17:18
    prop "text" of <Label> reads a signal eagerly, so it is read once, when the
    component renders, and never updates. ...
```

### render and act

Renders a component in a headless page with devtools installed before the app loads. Each `--act` dispatches an interaction (`click`, `input`, `change`, `submit`, `keydown`, `keyup`, `focus` or `blur`) and reports what it caused:

```sh
xote-lens render Counter --act "click #inc"
```

```text
Counter (src/Counter.res.mjs) rendered client-side
  graph: 1 signal, 3 computeds, 2 effects (2 bindings)
  html: <div id="counter"><p id="value">0</p>...
click #inc
  1 write · 3 computeds · 2 effects (2 bindings) · 2 DOM writes · scopes +0/-0
  wrote signal "count" = 1  (src/Counter.res.mjs:37:39)
  ran   effect #5 (text → p#value)
  ran   computed "doubled"  (src/Counter.res.mjs:10:29)
```

Read the counts as a reactive budget. An update that should touch one text node should show one DOM write, and a reorder should create no scopes. `--settle <ms>` keeps recording after each act, for async work.

### why

Explains the last update of an element (by selector) or a node (by id):

```sh
xote-lens why Counter "#doubled" --act "click #inc"
```

```text
why #doubled
  effect #6 ran
  └─ computed #4 recomputed  (src/Counter.res.mjs:33:29)
     └─ computed "doubled" recomputed  (src/Counter.res.mjs:10:29)
        └─ signal "count" written  (src/Counter.res.mjs:37:39)
```

### graph

Prints every node with its value, edges, scope and creation site, plus the scope tree. `--around <id> --depth <n>` limits it to one node's neighbourhood.

### expand

Shows what `@xote.component` did to a module, under each source line:

```text
14 │     <p id="value"> {Signal.get(count)} </p>
   │                     ^ reactive child: re-runs when the signals it reads change
17 │     <Label text={Int.toString(Signal.get(count))} />
   │                  ^ one-shot prop text of <Label>: read once, never updates
```

It reads the site map the ppx writes when given `-sitemap`. Add the flag to your `rescript.json`:

```json
"ppx-flags": [["xote/ppx/ppx", "-sitemap"]]
```

The emitted JavaScript is identical with or without the flag.

## Server Rendering

### SSR and Hydration

`--ssr` renders on a separate server process with no DOM, so `SSRContext.isServer` really is true. `--hydrate` then hydrates that markup in the page and compares it with what the client renders on its own. Each difference is a `hydration-mismatch` error, at a path like `div#greeting > p [class]`.

In hydrate mode the server's `SSRState` payload is in place before the app's modules load. Each key is reported with its server value and the client signal it was restored into:

```text
  ssr state:
    "visits" = 42: restored → signal "visits"
    "theme" = "dark": could not be decoded → signal "theme"
    "orphan" = true: sent, never restored
    "cart": restored, but the server never sent it → signal "cart"
```

`--markers` outlines the server markup and names every hydration marker: `<!--$-->` reactive text, `<!--#-->` reactive fragment, `<!--kl-->` keyed list, `<!--k:a-->` keyed row `a`, `<!--lc-->` component.

## Diagnostics

### Rules

| Rule | From | Finds |
|---|---|---|
| `compile-error`, `compiler-warning-N` | `check` | The compiler's findings, with locations |
| `effect-returns-unit` | `check` | An effect body returning `unit` instead of `option<unit => unit>`, with the fix |
| `one-shot-prop` | `check` | A user-component prop that reads a signal eagerly, so it is read once and never updates |
| `possible-hidden-read` | `check` | A `View.probe` site: a call the ppx cannot see into |
| `raw-captures-binding` | `check` | `%raw` code naming a surrounding ReScript binding |
| `unresolved-read` | `render` | A probe site that did read a signal: a leaf that will not update |
| `get-in-effect` | `render` | An effect that writes a signal it also reads |
| `leaked-effect` | `render` | An effect still running after its scope was released |
| `undisposed-computed` | `render` | A computed still subscribed after its scope was released |
| `unowned-effect` | `render` | An effect created inside another run, with no scope to own it |
| `hydration-mismatch` | `render --hydrate` | Server markup that differs from the client's |
| `ssr-state-decode-failed` | `render --hydrate` | A server value the client's codec cannot decode |
| `ssr-state-unrestored` | `render --hydrate` | A key the server sends that nothing restores |
| `ssr-state-missing` | `render --hydrate` | A key the client restores that the server never sent |
| `console` | `render` | Anything the app printed with `console.warn` or `console.error` |

## For Agents

### MCP Server

`xote-lens mcp` serves every command as an MCP tool over stdio. For Claude Code, add it to `.mcp.json` in your project:

```json
{
  "mcpServers": {
    "xote-lens": {
      "command": "node",
      "args": ["/path/to/xote/lens/bin/xote-lens.mjs", "mcp"]
    }
  }
}
```

The tools are `xote_api`, `xote_check`, `xote_expand`, `xote_render`, `xote_act`, `xote_why`, `xote_graph`, `xote_inspect`, `xote_html` and `xote_diagnostics`. Each returns the same JSON the CLI prints with `--json`. `xote_render` starts a fresh session in a new process, so it always sees freshly built modules, and the other session tools act on the latest render.

### A Good Loop

1. `xote_api` before using an API: only what it lists is public.
2. Edit, then `xote_check` to build and catch Xote-specific mistakes.
3. `xote_render`, then `xote_act`. Read the counts and diagnostics, and use `xote_why` for anything that updated, or failed to update, unexpectedly.

### Programmatic Use

```js
import { createSession } from "xote-lens"

const session = await createSession({ root: process.cwd() })
await session.render({ target: "Counter" })
const act = await session.act({ action: "click", selector: "#inc" })
console.log(act.counts, session.why({ selector: "#value" }))
session.close()
```

A session renders once, because module state cannot be reset in place. Render again in a new process.
