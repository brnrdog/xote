Devtools show what a Xote app does when it updates: which signal was written and where, which computeds and effects ran because of it, which DOM nodes changed, and why. The same data is available in three places: in code through `Devtools`, in the page through the [panel](/docs/devtools/panel), and in a terminal or an AI agent through [xote-lens](/docs/devtools/xote-lens).

> **Info:** The reactive graph comes from the debug hooks of `rescript-signals` (`Signals.Debug`), which are not in a published release yet. Without them, devtools still report scopes, DOM writes, keyed-list passes and hydration, and `Devtools.status()` says the graph is not visible. [Try it before the release](#try-it-before-the-release) shows how to link them in.

## Overview

### What Devtools See

Fine-grained reactivity fails quietly. A missing dependency gives a stale UI, not an error. An over-broad tracked block gives a slow UI, and an undisposed computed is a leak. A component tree shows none of this, because Xote components run once. Devtools show the three things that decide how an app behaves:

- **The reactive graph**: every signal, computed and effect, what each one reads, and the order the scheduler runs them in.
- **Scopes**: the keyed rows, fragment passes and boundaries that own reactive state, and so decide what is released when.
- **The DOM writes**: which binding wrote which node, and what caused it.

Every node and scope gets an id in creation order, so the same program driven the same way produces the same ids. That is what lets an agent refer to "node 17" across several calls.

### Where It Lives

`Devtools` and `DevtoolsPanel` ship in the `xote/devtools` entry. No other entry imports them, so they stay out of your client bundle. The renderer's instrumentation points do ship with it, each guarded by a single flag. Together they add about 0.4 KiB gzip to the full client bundle and do nothing until devtools are installed.

## Using Devtools

### Installing

Install devtools in your entry module, before anything reactive is created. Nodes created earlier have no id and are not reported.

```rescript
let status = Devtools.install()
/* status.signals: whether the reactive graph is visible */

/* ...create signals, mount the app... */
```

`install` takes `~captureStacks` (default `true`), which records where each node was created and where each write happened. Pass `false` for less overhead. Sites point at the compiled `.res.mjs`, which sits next to its `.res` source.

Name long-lived signals so they show up by name:

```rescript
let count = Signal.make(0, ~name="count")
let total = Computed.make(() => Signal.get(price) * Signal.get(qty), ~name="total")
```

### Reading the Graph

```rescript
let snapshot = Devtools.snapshot()
/* snapshot.nodes: id, kind, name, value preview, sources, observers, scope, site, binding */
/* snapshot.scopes: id, kind, key, parent, disposed */

let node = Devtools.inspect(12)
let writers = Devtools.writersOf(element) /* the bindings that write a DOM node */
```

A **binding** is an effect the renderer creates to keep one DOM node in step with a signal. Its `binding` field says what it writes (`text`, `attr:class`, `fragment` or `list`) and where.

### Why Did It Run?

`Devtools.why(id)` explains a node's last run as a tree of causes. It starts at the binding that wrote the DOM, goes through the computeds that recomputed, and ends at the signal writes that started it, with the code location of each write.

```rescript
switch Devtools.writersOf(element)->Array.get(0)->Option.flatMap(Devtools.why) {
| Some(cause) => Console.log(cause)
| None => Console.log("static: nothing writes this element")
}
```

```text
effect #6 (text → p#total) ran
└─ computed "total" recomputed
   └─ signal "qty" written  (src/Cart.res.mjs:41:7)
```

### Reactive Budgets

`Devtools.record(fn)` returns everything `fn` caused, synchronously, with counts. `Devtools.Budget.check` asserts those counts. Use it in tests to make fine-grained updates a tested property: an update that should touch one text node should cost one DOM write, and a reorder should build no rows.

```rescript
test("incrementing touches one text node", () => {
  let trace = Devtools.record(() => Signal.set(count, 1))
  assertEqual(
    Devtools.Budget.check(trace, ~writes=1, ~bindings=1, ~domWrites=1, ~scopesCreated=0),
    Ok(),
  )
})
```

The counts are `writes`, `effects`, `computeds`, `bindings`, `domWrites`, `scopesCreated`, `scopesDisposed` and `reconciled` (keyed passes). `Error` names every count that did not hold.

### Leaks

`Devtools.leaks()` reports three things:

- an effect still running after the scope that created it was released,
- a computed still subscribed after its scope was released,
- an effect created inside another node's run with no scope to own it, so every run of the outer node creates another.

### Muting a Tool's Own UI

A devtool built with Xote would show up in its own data. Wrap what it creates in `Devtools.mute`: those nodes, their scopes and their DOM writes are hidden now and on every later run.

```rescript
let toolState = Devtools.mute(() => Signal.make(0))
```

## Reference

### Events

`Devtools.subscribe(listener)` receives the merged event stream and returns the function that unsubscribes. `Devtools.history()` returns the most recent events. In JavaScript each event is an object whose `type` field names it, except `BatchStart` and `BatchEnd`, which are those strings.

| Event | Meaning |
|---|---|
| `Created` | A signal, computed or effect, with its name, scope and creation site |
| `Linked` / `Unlinked` | A dependency edge added, or dropped by re-tracking |
| `Written` | A `Signal.set`, whether it changed the value, and where it happened |
| `RunStart` / `RunEnd` | A computed recompute or an effect run; `RunEnd` says whether a computed's value changed |
| `Disposed` / `Collected` | Disposed explicitly, or reclaimed by the garbage collector |
| `BatchStart` / `BatchEnd` | The outermost `Signal.batch` |
| `ScopeCreated` / `ScopeDisposed` | A keyed row, fragment pass, boundary or region |
| `DomWrite` | A binding wrote text or an attribute |
| `Reconciled` | One keyed pass: kept, created, removed, moved, rebuilt |
| `Caught` | An error boundary caught a failure |
| `HydrationWarning` | The hydration walker could not match the server markup |
| `Probe` | A `View.probe` site was evaluated, and whether it read a signal |
| `StateRestored` | `SSRState.restore` on the client: whether the key was sent and decoded |

### Try It Before the Release

Until a `rescript-signals` release includes `Signals.Debug`, link the branch that has it into your project. The examples assume the two repositories are checked out side by side:

```sh
git clone -b brnrdog/nice-pascal-9c7ixn https://github.com/brnrdog/rescript-signals
git clone -b brnrdog/nice-pascal-9c7ixn https://github.com/brnrdog/xote

cd your-app   # or xote itself
npm install --no-save ../rescript-signals/packages/rescript-signals
npx rescript
```

`--no-save` leaves `package.json` and the lockfile alone. The next plain `npm install` restores the published release. Check that the hooks were found:

```rescript
Console.log(Devtools.install()) /* {signals: true, copies: 1} */
```

To work on devtools inside the Xote repository, link the branch the same way and run its suites. `npm run ppx:test` and `npm run lens:test` need `ocamlopt`.

```sh
npm test            # the library suites, the export snapshot and the consumer boundary
npm run ppx:test    # the ppx, including its site map
npm run lens:test   # xote-lens against a fixture app
```

Without the hooks, the tests that need the graph report as skipped rather than passing.
