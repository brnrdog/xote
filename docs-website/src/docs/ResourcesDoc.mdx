A resource turns asynchronous work, like a fetch, into a signal. `View.Suspense` shows a fallback while the resources below it load for the first time.

> **Info:** A resource is a `Signal.t` of its loading state. Read it with `Signal.get` like any other signal.

## Create a resource

`Resource.make` takes a function that returns a promise, and starts it right away. Here `Api.getUser` stands for your own function that returns `promise<user>`; [Fetching data](/docs/guides/fetching-data) shows how to write one.

```rescript
let userId = Signal.make("1")

let user = Resource.make(async () => {
  let id = Signal.get(userId) // a dependency: read before the first await
  await Api.getUser(id)
})
```

The function runs in an effect. The signals it reads **before its first `await`** are its dependencies: change `userId` and the resource fetches again. Reads after an `await` aren't tracked.

## Read its state

A resource holds one of four states:

- `Pending`: fetching with no value yet, on the first fetch or after a failure.
- `Ready(value)`: the latest fetch settled with `value`.
- `Refreshing(value)`: fetching again, with the previous `value` kept.
- `Failed(exn)`: the latest fetch threw or rejected.

```rescript
module UserName = {
  @xote.component
  let make = () =>
    <p>
      {switch Signal.get(user) {
      | Pending => "Loading..."
      | Ready(user) | Refreshing(user) => user.name
      | Failed(_) => "Could not load the user"
      }}
    </p>
}
```

`Resource.value` returns the value a state carries, if any, and `Resource.isLoading` tells whether a fetch is in flight.

## Refetch or set the value

`Resource.refetch` fetches again with the same dependencies. `Resource.mutate` sets the value directly, which is useful for optimistic updates, and drops any fetch in flight.

```rescript
<button onClick={_ => Resource.refetch(user)}> {"Reload"} </button>
```

Only the latest fetch can settle the state. If the user switches from one id to another and the first response arrives last, it's ignored.

## Combine and chain resources

A view that needs several resources would otherwise match on several states. `Resource.map2` combines two resources into one, so it reads one state:

```rescript
let page = Resource.map2(user, settings, (user, settings) => {user, settings})
```

The combined resource is `Failed` as soon as one of them has failed, `Pending` while one has no value yet, and the combined value otherwise, shown as `Refreshing` while either refreshes. `Resource.map` derives from one resource, `map3` from three, and `Resource.all` from an array of resources of the same type. The function runs again only when a value changes, not when a resource merely starts or stops refreshing, so keep it pure.

When a fetch needs another resource's value, use `Resource.chain`:

```rescript
let posts = user->Resource.chain(user => Api.getPosts(user.id))
```

The posts are fetched once the user has loaded, and again each time the user loads anew, but not while the user is only refreshing. Until then, the chain is `Pending` (or `Failed` if the user failed), and while the user refreshes it shows `Refreshing` with the posts it has.

`Resource.refetch` on a combined resource fetches every resource it combines; on a chain it runs the chain's own fetch again. `Resource.mutate` sets a chain's value, but does nothing on a combined resource: set the resources it combines instead.

## Handle errors

A failed fetch is a state like any other. To hand it to a [`View.ErrorBoundary`](/docs/api/view#view-errorboundary) instead, throw it where the state is read:

```rescript
switch Signal.get(user) {
| Failed(exn) => throw(exn)
| state => ...
}
```

## Suspense

To show a fallback while loading, wrap the components that create resources in [`View.Suspense`](/docs/api/view#view-suspense):

```rescript
<View.Suspense fallback={<p> {"Loading..."} </p>}>
  <Profile id />
  <Posts id />
</View.Suspense>
```

The fallback shows until every resource created below the suspense has loaded once. The children render straight away, hidden, so their fetches start at once and their state survives the wait. Their refs and `onMount` callbacks wait until they're shown.

### Suspense rules

- A resource suspends the nearest `Suspense` above the component that **created** it, wherever it is read. To wait for one created elsewhere, use `Resource.hold` (below).
- A combined resource (`map`, `map2`, `map3`, `all`) fetches nothing, so it doesn't suspend anything by being created; `hold` it to make a suspense wait for it. A `chain` fetches, so it suspends like `Resource.make`, until it first has a value or fails.
- A resource counts once. A later fetch shows as `Refreshing` and never brings the fallback back.
- Suspenses nest. The nearest one waits, and an inner subtree that is ready stays hidden while an outer suspense still waits.
- Removing a component releases its resources: a fetch in flight is dropped, and a suspense waiting for it stops waiting.

### Wait for a resource created elsewhere

A resource created at module level, or in a component above the suspense, doesn't make the suspense wait. Call `Resource.hold` in a component below the suspense to make it wait for one:

```rescript
let currentUser = Resource.make(() => Api.getCurrentUser())

module Greeting = {
  @xote.component
  let make = () => {
    Resource.hold(currentUser)
    <h1> {Signal.get(currentUser)->Resource.value->Option.mapOr("", user => user.name)} </h1>
  }
}
```

The wait follows the same rule as for a resource created below the suspense: the fallback shows until the resource first has a value or fails, and never again. A resource that already has a value holds nothing. Removing the component ends its hold. Call it once for each resource to wait for several.

### Show that something is refreshing

The fallback only covers the first load. To show that a refetch is in progress, call `View.Suspense.pending()` in a component below the suspense. It returns a signal that is `true` while any resource the suspense counts, created below it or held with `Resource.hold`, is fetching:

```rescript
module Toolbar = {
  @xote.component
  let make = () => {
    let refreshing = View.Suspense.pending()
    <div class={Signal.get(refreshing) ? "toolbar dimmed" : "toolbar"}>
      <ReloadButton />
    </div>
  }
}
```

Only the nearest suspense counts: a resource below a nested `Suspense` counts toward that one. Call `pending()` in a component body; called anywhere else it can't tell which suspense it's under, and logs a warning in development. Outside any suspense it is always `false`.

## Async values

`Resource` keeps loading in a state you match on. `Async.make` takes the other road: an async value is a plain `Signal.t` of the value itself, so it is read like any signal, and Xote waits for it where it is read.

```rescript
let userId = Signal.make("1")
let user = Async.make(() => Api.getUser(Signal.get(userId)))

module UserName = {
  @xote.component
  let make = () => <h2> {Signal.get(user).name} </h2>
}
```

What the function reads before its first `await` is its dependencies, as with `Resource.make`. Until the first value arrives, a read throws `Async.NotReady`. Xote treats that as "not yet", never as a failure:

- A JSX child or attribute, a `View.tracked` block, a list or a `Show` that reads the value renders once it is there. A `Computed` that reads it holds `NotReady` and recomputes when the value arrives.
- Under a `View.Suspense`, the fallback shows until the value arrives, and `View.Suspense.pending()` is `true` meanwhile.
- An error boundary lets it pass. A fetch that rejects is a failure, and goes to the boundary.

While a later fetch is in flight, reads return the previous value. `Async.isPending(() => Signal.get(user))` tells whether anything it read is still loading, so a view can dim itself.

Read an async value where Xote can wait for it. A component body runs once and untracked, so a `let` that reads a value not ready yet there is an error that says so: move the read into JSX, a `View.tracked` block or a `Computed`.

During a server render no fetch starts, and the value is never ready: the server renders what does not depend on it, and the client fetches once it hydrates.

Use `Async` when you want to derive with ordinary code (`Signal.get(user).name`) and let `Suspense` handle loading. Use `Resource` when you want the loading and failure states as values in your view, with `refetch` and `mutate`.

## Server rendering

During a [server render](/docs/advanced/ssr) (`SSR.renderToString`) nothing is awaited: no fetch starts, and `Suspense` renders its fallback. A resource created outside a render, at module level in a server process, isn't covered and does fetch, so create resources in components. Hydration then renders the children in the browser, where the resources fetch.

To handle failures with a boundary, see [error boundaries](/docs/learn/lifecycle). For loading, refetching and search patterns, see [Fetching data](/docs/guides/fetching-data).
