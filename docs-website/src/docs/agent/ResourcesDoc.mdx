## Summary

A resource (`Resource.make`) is a signal of the loading state of an async function: `Signal.t<Resource.state<'a>>`. The fetch runs inside an effect, so every signal it reads (tracked) **before its first `await`** is a dependency, and a change to any dependency starts a new fetch. Only the latest fetch can settle the state; an earlier one that resolves late is ignored. `View.Suspense` shows a fallback until the resources created below it (or held below it with `Resource.hold`) settle once, and `View.Suspense.pending()` reports refetches it does not cover; a `Failed` state can be thrown to a `View.ErrorBoundary`. The rule that matters most: read every input signal before the first `await`, or changes to it will not refetch.

## Rules

1. `Resource.make(fetch)` creates the state signal with value `Pending` and immediately runs `fetch` inside an effect (unless a server render is in progress, see rule 13).
2. The dependencies of a resource are exactly the signals read (tracked) while `fetch()` runs synchronously, that is, up to its first `await`. Reads after an `await` are not dependencies.
3. When a dependency changes, the effect re-runs: the state moves to `Refreshing(previousValue)` if it held a value (`Ready` or `Refreshing`), otherwise to `Pending` (from `Pending` or `Failed`), and `fetch` is called again.
4. Each fetch gets a version number. A fetch settles the state only if no later fetch, `mutate` or disposal has happened since it started. Late results of superseded fetches are dropped silently.
5. A fetch that returns a rejected promise, or throws synchronously, settles as `Failed(exn)`. A failure that happens while rendering the settled value is not a fetch failure and does not produce `Failed`.
6. `Resource.refetch(r)` re-runs the fetch with the same dependencies (same transitions as rule 3). It is a no-op for a resource created during a server render.
7. `Resource.mutate(r, v)` sets `Ready(v)` immediately and invalidates any fetch in flight (its result is dropped). The next dependency change or `refetch` fetches again.
8. A resource created while a component renders is owned by that component: disposing the component drops the fetch in flight (its result is ignored) and, if a `View.Suspense` was waiting for it, ends that wait.
9. A resource created outside any render (module level, event handler) has no owner and lives for the rest of the program.
10. A resource suspends the nearest `View.Suspense` above the component that **created** it, regardless of where its state is read.
11. A resource counts toward its suspense only once: the suspense waits until the first settle (`Ready`, `Failed`, or `mutate`). Later fetches show as `Refreshing` and never bring the fallback back.
12. Nested suspenses: the nearest one waits for its own resources; a ready inner subtree stays hidden while an outer suspense still waits.
13. During `SSR.renderToString` / `SSR.renderDocument` no fetch starts and the resource stays `Pending` forever on the server. `View.Suspense` renders its `fallback` into the HTML. A resource created at module level in a server process is not inside a render, so it does fetch.
14. To send a failure to an error boundary, throw it where the state is read inside the render tree: `| Failed(error) => throw(error)` in a reactive leaf or region.
15. `Resource.hold(r)`, called in a component body, makes the nearest `View.Suspense` of that component wait for `r` wherever `r` was created. It follows rule 11: the wait lasts until `r` first leaves `Pending` (a value, a failure, or `mutate`) and never comes back; a resource that is already `Ready`, `Refreshing` or `Failed` holds nothing. The hold is released with the calling component. Outside any `Suspense`, and during a server render, `hold` does nothing.
16. `View.Suspense.pending()`, called in a component body, returns a `Signal.t<bool>` that is `true` while any resource counting toward the nearest `Suspense` (created below it, or held below it while the hold lasts) has a fetch in flight: the first fetch and every later one. A fetch that replaces one still in flight does not make it flicker to `false`. It counts the nearest suspense only, not nested ones. Outside any `Suspense` it returns a signal that is always `false`.
17. `View.Suspense.pending()` reads which suspense it is under from the render in progress. Called outside a component body (an event handler, a timer, an effect's later run, an `onMount` callback) it logs a warning in development, and its result is whatever the frame installed at that moment gives.
18. `Resource.map(r, f)`, `map2`, `map3` and `all` return a *derived* resource: a `Resource.t` with no fetch of its own, whose state combines its sources' states. It is `Failed(e)` as soon as a source is `Failed` (the first in argument order), otherwise `Pending` while a source is `Pending`, otherwise `Refreshing(f(values))` while a source is `Refreshing`, otherwise `Ready(f(values))`.
19. A derived resource calls `f` again only when a source's **value** changes (by `===`). A source that only starts or stops refreshing keeps the derived value the same object. An `f` that throws makes the derived resource `Failed(exn)`. Its readers wake only when the state's case or value changes.
20. A derived resource does not suspend anything by being created (it fetches nothing). Its sources suspend where they were created; `Resource.hold(derived)` makes a suspense wait until every source has a value or one failed. It stays attached to its sources only while something reads it, like any computed.
21. `Resource.refetch(derived)` refetches every resource it derives from, each once even when reached through several paths. `Resource.mutate(derived, v)` does nothing.
22. `Resource.chain(source, fetch)` runs `fetch(value)` each time `source` settles as `Ready(value)` (and once, at creation, if `source` is already `Refreshing(value)`). It never fetches while `source` is `Pending`, `Failed` or only refreshing. Signals `fetch` reads before its first `await` are dependencies too, and only its latest call can settle the chain.
23. A chain's state: `Pending` / `Failed(e)` while `source` is; otherwise its own fetch state, with `Ready(v)` shown as `Refreshing(v)` while `source` refreshes. Created under a `View.Suspense`, a chain makes it wait until it first leaves `Pending` (which needs the source too), and counts toward `View.Suspense.pending()` while it is loading.
24. `Resource.refetch(chain)` runs the chain's own fetch again with the source's current value and does not refetch the source. `Resource.mutate(chain, v)` sets the chain's own value and drops its fetch in flight.
25. `Async.make(fetch)` (unreleased; needs rescript-signals 4) returns a `Signal.t<'a>` of the value itself, not a state. `fetch` runs at creation and again when a signal it read before its first `await` changes; only the latest fetch settles the value; while a later fetch is in flight, reads return the previous value. A rejected fetch makes reads throw the failure until a dependency changes and a fetch succeeds.
26. Until the first value, a read throws `Async.NotReady`. It is never a failure in Xote: a reactive leaf (JSX child or attribute), `View.tracked` block, `Show`/`For`/list or `Effect` that reads it waits and renders once the value arrives; a `Computed` holds it and recomputes then; `View.ErrorBoundary` lets it pass.
27. An effect (including the effect behind every reactive leaf and block) created under a `View.Suspense` whose run ends in `NotReady` makes that suspense wait — fallback shown, refs and `onMount` held — and counts toward `View.Suspense.pending()`, until a run gets past it or the effect is disposed. Each time the value is missing again (after a failure, while refetching) it waits again.
28. A read of a value not ready yet in a component body (an eager `let`) is an error: the body runs once and untracked, so it would never see the value arrive. Read it in JSX, a `View.tracked` block, a `Computed` or an `Effect`.
29. During a server render `Async.make` starts no fetch and the value is never ready: text renders empty, attributes are omitted, lists and blocks render nothing. On the client, hydration fetches and fills them in.
30. `Async.isPending(fn)` is `true` while `fn` read something still loading (a first load or a fetch again, directly or through a computed). Its reads are tracked, so a leaf that asks updates when the answer changes.

### State machine

| From | Event | To |
| --- | --- | --- |
| (created) | `Resource.make` (client) | `Pending`, fetch starts |
| `Pending` | fetch resolves with `v` | `Ready(v)` |
| `Pending` | fetch rejects or throws `e` | `Failed(e)` |
| `Ready(v)` | dependency change or `refetch` | `Refreshing(v)`, fetch starts |
| `Refreshing(v)` | fetch resolves with `w` | `Ready(w)` |
| `Refreshing(v)` | fetch rejects `e` | `Failed(e)` (the previous value is not kept) |
| `Failed(e)` | dependency change or `refetch` | `Pending`, fetch starts |
| any | `mutate(r, w)` | `Ready(w)`, in-flight fetch dropped |
| any | owner disposed | unchanged; in-flight fetch dropped |

## API

| Name | Signature | Behaviour |
| --- | --- | --- |
| `Resource.state` | `Pending`, `Ready('a)`, `Refreshing('a)`, `Failed(exn)` | Where a resource stands (see the state machine). |
| `Resource.t` | `Signal.t<state<'a>>` | A resource is a signal: read it with `Signal.get` (tracked) or `Signal.peek`. |
| `Resource.make` | `(unit => promise<'a>) => t<'a>` | Creates the resource and starts the first fetch (client only). |
| `Resource.refetch` | `t<'a> => unit` | Fetches again with the same dependencies. |
| `Resource.mutate` | `(t<'a>, 'a) => unit` | Sets `Ready(value)` now, drops any fetch in flight. |
| `Resource.value` | `state<'a> => option<'a>` | `Some(v)` for `Ready(v)` and `Refreshing(v)`, `None` otherwise. |
| `Resource.isLoading` | `state<'a> => bool` | `true` for `Pending` and `Refreshing`. |
| `Resource.map` | `(t<'a>, 'a => 'b) => t<'b>` | Derived resource of `f(value)` (rules 18–21). |
| `Resource.map2` | `(t<'a>, t<'b>, ('a, 'b) => 'c) => t<'c>` | Derived from two resources. |
| `Resource.map3` | `(t<'a>, t<'b>, t<'c>, ('a, 'b, 'c) => 'd) => t<'d>` | Derived from three resources. |
| `Resource.all` | `array<t<'a>> => t<array<'a>>` | Derived array of every value, in order. |
| `Resource.chain` | `(t<'a>, 'a => promise<'b>) => t<'b>` | Fetches with the source's value once it has one (rules 22–24). |
| `Async.make` | `(unit => promise<'a>, ~name: string=?) => Signal.t<'a>` | A signal of the value; reads throw `Async.NotReady` until it first arrives (rules 25–29). |
| `Async.NotReady` | `exception` | Thrown by a read of a value not there yet; Xote waits on it, never shows it as a failure. |
| `Async.isPending` | `(unit => 'a) => bool` | Whether `fn` read anything still loading (rule 30). |
| `Resource.hold` | `t<'a> => unit` | In a component body: makes the nearest `View.Suspense` wait for this resource until it first leaves `Pending` (rule 15). |
| `View.Suspense` | props `fallback?: node`, `children?: node` | Shows `fallback` until every resource created (or held) below has settled once. |
| `View.Suspense.pending` | `unit => Signal.t<bool>` | In a component body: `true` while a resource counting toward the nearest suspense is fetching, refetches included (rule 16). |
| `View.ErrorBoundary` | props `fallback: (exn, unit => unit) => node`, `onError?: exn => unit`, `children?: node` | Catches render/update failures below; `fallback` gets the error and a reset function. |

Note that `Resource.value` and `Resource.isLoading` take a **state**, not a resource: write `Resource.value(Signal.get(r))` or `Signal.get(r)->Resource.value`.

## Patterns

Use when a component loads data that depends on a prop or a signal: create the resource in the component and switch over its state.

```rescript
module UserCard = {
  @xote.component
  let make = (~userId: Signal.t<string>) => {
    let user = Resource.make(() => Api.getUser(Signal.get(userId)))
    <p>
      {switch Signal.get(user) {
      | Pending => "Loading…"
      | Ready(u) | Refreshing(u) => u.name
      | Failed(_) => "Could not load the user."
      }}
    </p>
  }
}
```

Use when loading and failure states should live outside the component: a `View.Suspense` for the first load and a `View.ErrorBoundary` for failures. The component that creates the resource MUST be inside the `Suspense`.

```rescript
module UserName = {
  @xote.component
  let make = (~userId: Signal.t<string>) => {
    let user = Resource.make(() => Api.getUser(Signal.get(userId)))
    <h2>
      {switch Signal.get(user) {
      | Failed(error) => throw(error)
      | Ready(u) | Refreshing(u) => u.name
      | Pending => ""
      }}
    </h2>
  }
}

module Profile = {
  @xote.component
  let make = (~userId: Signal.t<string>) =>
    <View.ErrorBoundary
      fallback={(_error, retry) =>
        <div>
          <p> {"Could not load the user."} </p>
          <button onClick={_ => retry()}> {"Try again"} </button>
        </div>}>
      <View.Suspense fallback={<p> {"Loading…"} </p>}>
        <UserName userId />
      </View.Suspense>
    </View.ErrorBoundary>
}
```

`retry` re-creates everything inside the boundary, so `UserName` runs again and creates a new resource, which fetches again.

Use when the user edits loaded data: update optimistically with `mutate`, then `refetch` after the save. Dim stale values with `Resource.isLoading`.

```rescript
module EditableName = {
  @xote.component
  let make = (~userId: Signal.t<string>) => {
    let user = Resource.make(() => Api.getUser(Signal.get(userId)))
    let rename = name => {
      Signal.peek(user)
      ->Resource.value
      ->Option.forEach(u => Resource.mutate(user, {...u, name}))
      Api.saveName(Signal.peek(userId), name)
      ->Promise.thenResolve(() => Resource.refetch(user))
      ->ignore
    }
    <div>
      <p class={Resource.isLoading(Signal.get(user)) ? "dim" : ""}>
        {Signal.get(user)->Resource.value->Option.mapOr("", u => u.name)}
      </p>
      <button onClick={_ => rename("Grace")}> {"Rename"} </button>
      <button onClick={_ => Resource.refetch(user)}> {"Reload"} </button>
    </div>
  }
}
```

Use when several components share one piece of remote state for the life of the page: create the resource at module level. It has no owner and is never disposed. Components under a `Suspense` that should wait for it call `Resource.hold`.

```rescript
let currentUserId = Signal.make("1")
let currentUser = Resource.make(() => Api.getUser(Signal.get(currentUserId)))

module Greeting = {
  @xote.component
  let make = () => {
    Resource.hold(currentUser)
    <h1> {Signal.get(currentUser)->Resource.value->Option.mapOr("", u => u.name)} </h1>
  }
}
```

Use when one view needs several resources: combine them, so the view matches on one state. Use `chain` when one fetch needs another's result.

```rescript
module Dashboard = {
  @xote.component
  let make = (~userId: Signal.t<string>) => {
    let user = Resource.make(() => Api.getUser(Signal.get(userId)))
    let settings = Resource.make(() => Api.getSettings())
    let posts = user->Resource.chain(u => Api.getPosts(u.id))
    let page = Resource.map3(user, settings, posts, (u, s, p) => (u, s, p))
    <section>
      {switch Signal.get(page) {
      | Pending => "Loading…"
      | Failed(_) => "Could not load the dashboard."
      | Ready((u, _, p)) | Refreshing((u, _, p)) =>
        u.name ++ ": " ++ Int.toString(Array.length(p)) ++ " posts"
      }}
    </section>
  }
}
```

Use when the page should show that a refetch is in progress without matching on every resource: read `View.Suspense.pending()` in any component under the suspense.

```rescript
module Toolbar = {
  @xote.component
  let make = () => {
    let refreshing = View.Suspense.pending()
    <div class={Signal.get(refreshing) ? "toolbar dimmed" : "toolbar"}>
      <button onClick={_ => Resource.refetch(currentUser)}> {"Reload"} </button>
    </div>
  }
}
```

## Anti-patterns

**Reading an input after the first `await`.**

```rescript
let wrong = Resource.make(async () => {
  let q = Signal.get(query)
  await Promise.resolve()
  await searchApi(q, Signal.get(page)) // page read after an await: not a dependency
})
```

Symptom: changing `page` does nothing; only changing `query` refetches. Correct: read every input first, then start the async work.

```rescript
let right = Resource.make(() => {
  let q = Signal.get(query)
  let p = Signal.get(page)
  searchApi(q, p)
})
```

Why: dependencies are recorded only while `fetch` runs synchronously (rule 2).

**Creating the resource above the `Suspense` that should wait for it.**

```rescript
@xote.component
let make = (~userId) => {
  let user = Resource.make(() => Api.getUser(Signal.get(userId)))
  <View.Suspense fallback={<p> {"Loading…"} </p>}>
    <UserView user />
  </View.Suspense>
}
```

Symptom: the fallback never shows; `UserView` renders `Pending` itself. Correct: create the resource inside a component rendered under the `Suspense` (see the `UserName` pattern), or call `Resource.hold(user)` in `UserView`. Why: a resource suspends the nearest suspense above the component that created it (rule 10), and here there is none.

**Calling `View.Suspense.pending()` from an event handler or an effect.**

Symptom: a development warning, and a signal that is always `false` or belongs to the wrong suspense. Correct: call it once in the component body and keep the signal. Why: it reads the suspense from the render in progress (rule 17).

**Swallowing failures under an error boundary.**

```rescript
{switch Signal.get(user) {
| Failed(_) => ""
| Ready(u) | Refreshing(u) => u.name
| Pending => ""
}}
```

Symptom: on failure the UI is blank and the boundary's fallback never appears. Correct: `| Failed(error) => throw(error)`. Why: an error boundary only sees errors thrown while rendering (rule 14); a resource never throws on its own.

**Creating a resource inside a reactive region or a list row render function that re-runs.**

Symptom: a new fetch on every re-run of the region (for example every time an `if` condition changes, or every `View.tracked` re-run), and earlier resources are disposed mid-flight. Correct: create the resource in a component body (runs once) or at module level, and read it in the region.

**Calling `Resource.make` from an event handler.**

Symptom: a resource with no owner per click; nothing disposes them, and nothing reads the old ones. Correct: create the resource once (component body or module level) and call `Resource.refetch` or change a dependency signal from the handler.

## Edge cases

- `Refreshing → Failed` drops the previous value: `Resource.value` returns `None` after a failed refresh.
- `mutate` while `Pending` under a `Suspense` ends the suspense wait (the resource has settled for the suspense's purposes).
- Signal equality: every settle writes a new `Ready(v)` value, so readers are notified even when `v` is structurally equal to the previous value.
- `View.Suspense` renders its children immediately, inside a wrapper `div` with `display: none` while waiting and `display: contents` after; their refs and `View.onMount` callbacks are held until the children are shown. CSS child selectors see these wrappers.
- `View.ErrorBoundary` also renders a `<div style="display: contents">` around its subtree.
- `Resource.mutate` on a derived resource (`map`, `map2`, `map3`, `all`) is a silent no-op: the type allows the call, but a derived value has nothing of its own to set. Mutate a source.
- A source that settles to a structurally equal but new value (a new object from a refetch) counts as a new value: a derived resource calls `f` again, and a chain fetches again.
- Cancellation: there is none. A superseded fetch keeps running; only its result is ignored. Pass an `AbortController` signal yourself if the request must be aborted.
- Ownership: a resource created in a component that is later removed stops affecting state; a resource at module level keeps re-fetching on dependency changes forever.

## SSR and hydration

- In a server render no fetch starts: a component's resource is `Pending` in the HTML, and `View.Suspense` writes its `fallback`.
- On the client, the `Suspense` region is rendered again rather than adopted, so its children mount and their resources fetch in the browser.
- To ship data with the HTML instead, load it on the server before rendering, put it in a signal, register that signal with `SSRState.sync` after it holds the data, and read the signal (not a resource) in the component. See `/docs/advanced/ssr`.
- A module-level resource in a server process fetches (it is not created during a render); its result is not serialized unless you transfer it through `SSRState` yourself.

## Verify

- Type errors to expect: passing a resource where a state is expected (`Resource.value(user)`) fails to compile; write `Resource.value(Signal.get(user))`. A `switch` missing `Refreshing` is a non-exhaustive match warning.
- Minimal jsdom test: mount a component whose fetch awaits a promise you control; assert the text is `Pending` (or the Suspense fallback) before resolving and the value after one macrotask (`await new Promise(r => setTimeout(r, 0))`).
- Dependency check: change a signal read after an `await` and assert that no new fetch started (count calls in the fetch function).
- Server check: `SSR.renderToString` of a component with a resource contains its `Pending` branch (or the Suspense fallback) and the fetch function is never called.
