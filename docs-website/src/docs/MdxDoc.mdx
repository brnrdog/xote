MDX lets Markdown files compile to Xote views. Use it when docs, articles or other long-form pages should live as `.mdx` files but still embed Xote components. This docs site is built that way.

> **Status:** The MDX runtime is deliberately small. It provides the JSX runtime bridge and helpers for component overrides; your bundler still compiles the MDX.

## Install the MDX plugin

Add the MDX Rollup plugin to the Vite app that imports `.mdx` files.

```bash
npm install --save-dev @mdx-js/rollup
```

For GitHub Flavored Markdown features such as tables, add `remark-gfm` too.

```bash
npm install --save-dev remark-gfm
```

## Configure Vite

Point MDX at Xote's automatic JSX runtime.

```js
// vite.config.js
import mdx from "@mdx-js/rollup"
import remarkGfm from "remark-gfm"
import { defineConfig } from "vite"

export default defineConfig({
  plugins: [
    mdx({
      jsxImportSource: "xote",
      jsxRuntime: "automatic",
      remarkPlugins: [remarkGfm],
    }),
  ],
})
```

With `jsxImportSource` set to `"xote"`, MDX uses the runtime exported from `xote/jsx-runtime` and `xote/jsx-dev-runtime`.

## Import MDX from ReScript

Bind the compiled MDX module as an `Mdx.document`, then render it to a [`View.node`](/docs/api/view#view-types).

```rescript
// ArticlePage.res
@module("./article.mdx") external article: Mdx.document = "default"

let app = () => {
  <main class="article-shell">
    {Mdx.render(article, ())}
  </main>
}

View.mountById(app(), "root")
```

## Override elements with components

`Mdx.render` takes an optional `components` dictionary. Keys are Markdown/HTML element names or the names of custom components used in the MDX; values are Xote components wrapped with `Mdx.component`.

```rescript
// ArticlePage.res
type mdxProps = {
  children?: Mdx.children,
  href?: string,
}

module Link = {
  let make = (props: mdxProps) => {
    <a href={props.href->Option.getOr("#")} target="_blank" attrs=[View.attr("rel", "noreferrer")]>
      {View.fragment(
        switch props.children {
        | Some(children) => Mdx.childrenToNodes(children)
        | None => []
        },
      )}
    </a>
  }
}

let components = Mdx.components([
  ("a", Mdx.component(Link.make)),
])

let page = Mdx.render(article, ~components, ())
```

## Render children

MDX children arrive as JavaScript values, because the MDX compiler decides their shape. Turn them back into Xote values with the `Mdx` helpers:

- `Mdx.childrenToNodes(children)` returns an array of [`View.node`](/docs/api/view#view-types).
- `Mdx.childrenToText(children)` extracts plain text, for things like syntax highlighting or heading ids.

```rescript
// ArticleHeading.res
type headingProps = {children?: Mdx.children}

module Heading = {
  let make = (props: headingProps) => {
    <h2 class="article-heading">
      {View.fragment(
        switch props.children {
        | Some(children) => Mdx.childrenToNodes(children)
        | None => []
        },
      )}
    </h2>
  }
}
```

## Write MDX with Xote components

An MDX file can mix Markdown, HTML-like tags, and named components supplied through the `components` dictionary.

```mdx
{/* article.mdx */}

# MDX with Xote

This paragraph renders as Xote nodes.

<Example />

<a href="https://mdxjs.com">MDX link rendered through a Xote component override</a>
```

Override Markdown output by key:

```rescript
// ArticlePage.res
let components = Mdx.components([
  ("h1", Mdx.component(ArticleTitle.make)),
  ("p", Mdx.component(LeadParagraph.make)),
  ("Example", Mdx.component(Example.make)),
])
```

## Tables and other GitHub Markdown

Enable `remark-gfm` when your content uses GFM syntax such as tables.

```mdx
{/* article.mdx */}

| Feature | Supported |
| --- | --- |
| Component overrides | Yes |
| Markdown tables | Yes, with `remark-gfm` |
```

Without `remark-gfm`, the base MDX parser reads pipe tables as plain paragraphs.

## What the runtime handles

Xote's MDX runtime turns MDX's automatic JSX calls into [`View.node`](/docs/api/view#view-types) values. It supports:

- HTML and SVG tags
- event props such as `onClick`
- static, signal, computed, and `MaybeSignal`-wrapped attributes
- fragments and nested children
- reserved `key` handling for keyed reconciliation
- MDX internal props such as `mdxType` and `originalType`

Everything else stays in the bundler: MDX parsing, remark and rehype plugins, syntax extensions and file loading. Configure those in Vite, or whatever build pipeline imports your `.mdx` files.

## Tips

- Keep MDX content about prose and examples; put stateful UI in named Xote components.
- Use overrides for links, code blocks, headings and demo panels, so MDX pages match the rest of your app.
- Type only the props each override needs, then wrap the component with `Mdx.component`.
- Add `remark-gfm` when your content uses tables, task lists, autolinks or strikethrough.
- MDX pages can be server-rendered and hydrated like any other view; see [Server rendering](/docs/advanced/ssr).
